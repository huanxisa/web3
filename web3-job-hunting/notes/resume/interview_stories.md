## W2 — Aave V3（借贷业务）⭐ 示范周

### 业务背景（1 分钟）

> Aave V3 是去中心化借贷协议，用户存入抵押资产可以借出其他资产。
>
> **后端必须做的事**：
> 1. **健康因子监控** — 价格波动可能让用户头寸瞬间变成"可清算"，钱包/Aave 安全告警系统必须毫秒级感知
> 2. **清算机器人** — 一旦健康因子 < 1，谁先调用 `liquidationCall` 谁拿清算奖励，是 MEV 红海

### 系统设计 #1：用户健康因子实时监控 + 推送系统（1.5 分钟）

> **场景**：DeFi 钱包推送 / Aave 官方安全告警，10 万用户级
>
> **架构**：3 模块流水线
> - **Listener**：go-ethereum 订阅 Pool 合约 Borrow/Supply/Repay 事件，写入 Postgres `user_positions` 表
> - **Calculator**：定时（10s）+ 事件驱动两条线，遍历活跃用户算 healthFactor，结果写 Redis ZSET（按健康度排序）
> - **Notifier**：监听 ZSET 变化，<1.1 触发 Webhook 推送，带去重 + 重试 + Webhook 失败告警
>
> **关键 tradeoff**：
> - **为什么不直接调 `getUserAccountData`** — 该接口需要 RPC 调用，10 万用户 ×10s = 1 万 QPS 顶不住，所以缓存到 Postgres + 只有"喂价/借还" 触发重算
> - **为什么 Postgres + Redis 双层** — Postgres 持久化用户头寸（reorg 安全），Redis 算实时排行榜（<1.1 用户的 ZSET 查询 O(logN)）
> - **reorg 处理** — 保留最近 12 块原始数据，超过 finality 才确认到主表
>
> **PoC 已开源**：<https://github.com/___/aave-health-monitor>

### 系统设计 #2：清算机器人架构（1.5 分钟）

> **场景**：MEV / 清算 keeper 公司
>
> **架构**：扫描 → 模拟 → bid 三段
> - **扫描**：复用健康因子模块的 Redis ZSET，<1 用户列表
> - **模拟**：本地 fork 链 + `liquidationCall` 模拟，算预期收益（清算奖励 - gas - swap 滑点）
> - **bid**：通过 Flashbots private bundle 上链，避免被前置交易抢跑
>
> **关键 tradeoff**：
> - **为什么不用 mempool watch** — 健康因子变化主要由喂价 update 触发，订阅事件比 mempool 简单且快
> - **为什么需要 Flashbots** — 清算赏金高，公开 mempool 100% 被 MEV bot 复制并抢跑
> - **风险控制** — 单次清算金额限制 + 余额监控 + 失败 N 次熔断

### 收尾（1 分钟）

> **学到的最关键点**：
> 1. Web3 后端的"实时性"通常 = "事件驱动 + 链上查询的成本权衡"，不能直接 RPC poll
> 2. reorg 处理是 Web3 后端跟传统后端最大的区别，必须设计在数据模型里
> 3. 清算这种 MEV 场景，技术栈必须包含 Flashbots/MEV-Boost
>
> **下次会怎么改进**：
> - 用 Kafka 替 Postgres 做事件流（写入更快 + 多消费者解耦）
> - 引入 Tenderly 做链上模拟，比本地 fork 更快

## 附：通用追问应对

| 面试官追问 | 标准答法（套到任何项目） |
|---|---|
| "如果规模翻 100 倍呢？" | 1) 算瓶颈在哪（CPU / 数据库 / RPC） 2) 给出 3 种扩展路径（垂直/水平/缓存）3) 选 1 种讲细 |
| "RPC 延迟 100ms 怎么办？" | multi-RPC + 健康检查 + 自动 fallback + 把所有 RPC 调用加 timeout |
| "数据一致性怎么保证？" | 区分链上 finality（12 块）+ 业务强一致（用 Postgres 事务）+ 最终一致（消息队列） |
| "你最自豪的设计？" | 健康因子模块的"事件驱动 + 定时兜底"两条线设计，避免漏算 |
| "你的项目跟 XX 公司的有什么不同？" | 我做的是 PoC 验证设计原则，生产级还需要补 X/Y/Z（坦诚 + 知道差距 = 加分） |

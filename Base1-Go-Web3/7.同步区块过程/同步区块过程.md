# Optimism L2 源码系列 - 同步区块过程

从 L1 的交易中还原出来的数据被命名为 PayloadAttributes，而 PayloadAttributes 成为 L2 执行层客户端的区块，还需要经过一系列的过程。

在最新的代码中 op-node 的所有的代码已修改为了事件驱动模式，所以把 PayloadAttributes 同步到 L2 执行层客户端生成新的区块，同样是由一系列的事件驱动的。

## 同步前的准备

当一个 `PayloadAttributes` 被加载好之后，由会被 `PipelineDeriver` 实例包裹成 `DerivedAttributesEvent` 事件发送出去：

```go
func (d *PipelineDeriver) OnEvent(ev event.Event) bool {
    switch x := ev.(type) {
    case // 忽略其他的事件分支
    case PipelineStepEvent:
       // Don't generate attributes if there are already attributes in-flight
       if d.needAttributesConfirmation {
          d.pipeline.log.Debug("Previously sent attributes are unconfirmed to be received")
          return true
       }
       d.pipeline.log.Trace("Derivation pipeline step", "onto_origin", d.pipeline.Origin())
       preOrigin := d.pipeline.Origin()
       attrib, err := d.pipeline.Step(d.ctx, x.PendingSafe)
       postOrigin := d.pipeline.Origin()
       if preOrigin != postOrigin {
          d.emitter.Emit(DeriverL1StatusEvent{Origin: postOrigin})
       }
       if err == io.EOF {
          // 省略一些代码...
       } else {
          if attrib != nil {
             d.needAttributesConfirmation = true
             d.emitter.Emit(DerivedAttributesEvent{Attributes: attrib})
          } else {
             d.emitter.Emit(DeriverMoreEvent{}) // continue with the next step if we can
          }
       }
    }
    return true
}
```

接着这个 `DerivedAttributesEvent` 事件会被 `AttributesHandler` 接受并处理，这时会派生出两个新的事件：

```go
case derive.DerivedAttributesEvent:
       eq.attributes = x.Attributes
       eq.emitter.Emit(derive.ConfirmReceivedAttributesEvent{})
       // to make sure we have a pre-state signal to process the attributes from
       eq.emitter.Emit(engine.PendingSafeRequestEvent{})
```

在发送两个事件之前，这个事件中持有的最新的 PayloadAttributes 的引用会复制跟当前的 `AttributesHandler` 实例的 `attributes` 字段

其中，`ConfirmReceivedAttributesEvent` 事件触发相关组件的状态更新。

而 `PendingSafeRequestEvent` 事件在被发送后，被 `EngDeriver` 实例接收并处理：

```go
case PendingSafeRequestEvent:
    d.emitter.Emit(PendingSafeUpdateEvent{
       PendingSafe: d.ec.PendingSafeL2Head(),
       Unsafe:      d.ec.UnsafeL2Head(),
    })
```

会从 `EngineController` 实例中取当前 L2 节点的最新的 Block 状态，然后发送 `PendingSafeUpdateEvent` 事件。

`PendingSafeUpdateEvent` 事件会被两个处理器监听并处理，分别是 `StatusTracker` 和 `AttributesHandler`。

StatusTracker 会保存临时状态，对流程无影响。

而再次出现的 `AttributesHandler` 实例，则相当于刚刚的这一系列的事件，是为了获取当前节点的最新状态。这种做法是为了减少各个组件之间的依赖。

继续跟进流程，`AttributesHandler` 实例收到 `PendingSafeUpdateEvent` 事件后，会执行 onPendingSafeUpdate 方法，并且事件会被作为参数传入：

```go
func (eq *AttributesHandler) onPendingSafeUpdate(x engine.PendingSafeUpdateEvent) {
    // 省略一些其他流程的代码...

    if eq.attributes.Parent != x.PendingSafe {
       // If the attributes are supposed to follow the pending safe head, but don't build on the exact block,
       // then there's some reorg inconsistency. Either bad attributes, or bad pending safe head.
       // Trigger a reset, and the system can derive attributes on top of the pending safe head.
       // Until the reset is complete we don't clear the attributes state,
       // so we can re-emit the ResetEvent until the reset actually happens.

       eq.emitter.Emit(rollup.ResetEvent{Err: fmt.Errorf("pending safe head changed to %s with parent %s, conflicting with queued safe attributes on top of %s",
          x.PendingSafe, x.PendingSafe.ParentID(), eq.attributes.Parent)})
    } else {
       // if there already exists a block we can just consolidate it
       if x.PendingSafe.Number < x.Unsafe.Number {
          eq.consolidateNextSafeAttributes(eq.attributes, x.PendingSafe)
       } else {
          // append to tip otherwise
          eq.sentAttributes = true
          eq.emitter.Emit(engine.BuildStartEvent{Attributes: eq.attributes})
       }
    }
}
```

其他的流程先不理会，重点关注 `eq.attributes` 字段会被如何处理:

当前最新的 PendingSafe 区块如果与 `eq.attributes` 的父区块信息**不相同**，那么发送 `ResetEvent`,这时需要重置一些状态。

当前最新的 PendingSafe 区块如果与 `eq.attributes` 的父区块信息**相同**，就是普通流程，即当前区块与上个区块连续，发送 `BuildStartEvent` 事件，正式开始的更新 L2 执行层客户端区块的流程。

## 构建新区块

`BuildStartEvent` 事件会被 `EngDeriver`，然后调用 `onBuildStart` 方法:

```go
func (eq *EngDeriver) onBuildStart(ev BuildStartEvent) {
    // 省略一些代码...

    fcEvent := ForkchoiceUpdateEvent{
       UnsafeL2Head:    ev.Attributes.Parent,
       SafeL2Head:      eq.ec.safeHead,
       FinalizedL2Head: eq.ec.finalizedHead,
    }
    
    // 省略一些代码...
    
    fc := eth.ForkchoiceState{
       HeadBlockHash:      fcEvent.UnsafeL2Head.Hash,
       SafeBlockHash:      fcEvent.SafeL2Head.Hash,
       FinalizedBlockHash: fcEvent.FinalizedL2Head.Hash,
    }
    buildStartTime := time.Now()
    id, errTyp, err := startPayload(ctx, eq.ec.engine, fc, ev.Attributes.Attributes)
    
    // 省略一些错误流程处理代码...
    
    eq.emitter.Emit(fcEvent)

    eq.emitter.Emit(BuildStartedEvent{
       Info:         eth.PayloadInfo{ID: id, Timestamp: uint64(ev.Attributes.Attributes.Timestamp)},
       BuildStarted: buildStartTime,
       IsLastInSpan: ev.Attributes.IsLastInSpan,
       DerivedFrom:  ev.Attributes.DerivedFrom,
       Parent:       ev.Attributes.Parent,
    })
}
```

这个方法中，初始化了一个 `ForkchoiceUpdateEvent` 实例，记录当前状态。

并且 `ForkchoiceUpdateEvent` 中的字段值，以及时间中的 `PayloadAttributes` 实例被作为参数传入 `startPayload` 方法中。

在 startPayload 方法中，会使用 http 远程调用执行层客户端的 `engine_forkChoiceUpdate` API，根据 attributes 的特征选择 API 的 V1\V2\V3 版本。

其中最重要一点是 `engine_forkchoiceUpdate` API 在 attributes 参数不为空时，即包含交易时，会返回一个 payloadId，这个 id 是一个 hash 值，可以使用这个 id 从执行层客户端查询到新区块的 `ExecutionPayload` 数据。

`ForkchoiceUpdateEvent` 事件是为了当前 op-node 中的组件更新各自的状态。

而 `BuildStartedEvent` 事件还是会被 `EngDeriver` 接收并处理，调用 onBuildStarted 方法：

```go
func (eq *EngDeriver) onBuildStarted(ev BuildStartedEvent) {
    // If a (pending) safe block, immediately seal the block
    if ev.DerivedFrom != (eth.L1BlockRef{}) {
       eq.emitter.Emit(BuildSealEvent{
          Info:         ev.Info,
          BuildStarted: ev.BuildStarted,
          IsLastInSpan: ev.IsLastInSpan,
          DerivedFrom:  ev.DerivedFrom,
       })
    }
}
```

`BuildStartedEvent` 事件中大部分字段会被用来构建新的事件——`BuildSealEvent`。

并且 `BuildSealEvent` 还是会被 `EngDeriver` 实例接收，并调用 `onBuildSeal` 方法：

```go
case BuildSealEvent:
    d.onBuildSeal(x)
```

而在 `onBuildSeal` 方法中，则会用到之前 `engine_forkchoiceUpdate` API 返回的 id:

```go
func (eq *EngDeriver) onBuildSeal(ev BuildSealEvent) {
    ctx, cancel := context.WithTimeout(eq.ctx, _buildSealTimeout_)
    defer cancel()

    sealingStart := time.Now()
    envelope, err := eq.ec.engine.GetPayload(ctx, ev.Info)

       // 省略处理错误流程代码...
    }

    if err := sanityCheckPayload(envelope.ExecutionPayload); err != nil {
      // 省略处理错误流程代码...
    }

    ref, err := derive.PayloadToBlockRef(eq.cfg, envelope.ExecutionPayload)
    if err != nil {
       // 省略处理错误流程代码...
    }

    // 省略指标统计部分代码...

```

这一步是使用 `payloadId` 从执行层客户端的 `engine_getPayload` API 中获取到 `ExecutionPayload`，如果之前的提交的交易数据有问题，那么这一步中，是无法用 `payloadId` 获取到 `ExecutionPayload`，这一步其实就是在验证区块数据是否有效。

在 `sanityCheckPayload` 则主要是按照 OP Stack Spec 定义的标准检查 `ExecutionPayload`，是否有交易，并且是否只有第一个交易是 DepositType，否则就是无效数据。

`PayloadToBlockRef` 则是通过 `ExecutionPayload` 中的数据，构建一个新的 L2 区块信息的引用。

获取到 `ExecutionPayload` 之后，再次发送 `BuildSealedEvent` 事件。事件依旧被 `EngDeriver` 接受并处理，并调用 onBuildSealed：

```go
case BuildSealedEvent:
    d.onBuildSealed(x)
```

`onBuildSealed` 方法，会把事件中的字段重新组织成新的 `PayloadProcessEvent` 事件：

```go
func (eq *EngDeriver) onBuildSealed(ev BuildSealedEvent) {
    // If a (pending) safe block, immediately process the block
    if ev.DerivedFrom != (eth.L1BlockRef{}) {
       eq.emitter.Emit(PayloadProcessEvent{
          IsLastInSpan: ev.IsLastInSpan,
          DerivedFrom:  ev.DerivedFrom,
          Envelope:     ev.Envelope,
          Ref:          ev.Ref,
       })
    }
}
```

`PayloadProcessEvent` 事件被 `EngDeriver` 实例接收并处理，调用 onPayloadProcess 方法：

```go
func (eq *EngDeriver) onPayloadProcess(ev PayloadProcessEvent) {
    // 省略部分代码...

    status, err := eq.ec.engine.NewPayload(ctx,
       ev.Envelope.ExecutionPayload, ev.Envelope.ParentBeaconBlockRoot)
    if err != nil {
       // 省略部分代码...
    }
    switch status.Status {
    case eth._ExecutionInvalid_, eth._ExecutionInvalidBlockHash_:
       // 省略部分代码...
    case eth._ExecutionValid_:
       eq.emitter.Emit(PayloadSuccessEvent(ev))
       return
    default:
       // 省略部分代码...
    }
}
```

这个方法中则比较简单，忽略掉部分错误流程的代码后，只做了两件事：

1. 把 `ExecutionPayload` 数据通过 `engine_newPayload` API 重新发送给执行层客户端。
2. 成功发送后，发送 `PayloadSuccessEvent` 事件。

这里因为 `PayloadProcessEvent` 的结构体和 `PayloadSuccessEvent` 的结构体的字段完全相同，所以 `ev` 可以直接强转位 `PayloadSuccessEvent` 类型。

`PayloadSuccessEvent` 事件同样会被 `EngDeriver` 并处理，并调用 `onPayloadSuccess` 方法，会发送 `PromotePendingSafeEvent` 事件和 `TryUpdateEngineEvent` 事件。

`PromotePendingSafeEvent` 事件也还是被 `EngDeriver` 接受，并处理：

```go
case PromotePendingSafeEvent:
    // Only promote if not already stale.
    // Resets/overwrites happen through engine-resets, not through promotion.
    if x.Ref.Number > d.ec.PendingSafeL2Head().Number {
       d.ec.SetPendingSafeL2Head(x.Ref)
       d.emitter.Emit(PendingSafeUpdateEvent{
          PendingSafe: d.ec.PendingSafeL2Head(),
          Unsafe:      d.ec.UnsafeL2Head(),
       })
    }
    if x.Safe && x.Ref.Number > d.ec.LocalSafeL2Head().Number {
       d.emitter.Emit(PromoteLocalSafeEvent{
          Ref:         x.Ref,
          DerivedFrom: x.DerivedFrom,
       })
    }
```

第一个 if 语句中，更新当前的 pendingSafeHead 的状态值。表示是在某个 spanbatch 中间的某个区块。

第二个 if 语句中，则是更新当前的 safeHead 的状态值。表示已经经过交叉验证之后的某个区块。经历一整个 spanbatch 之后，才会更新。

`TryUpdateEngineEvent` 事件依然是被 `EngDeriver` 收到，并处理，调用 `EngineController` 实例的 `TryUpdateEngine` 方法：

```go
func (e *EngineController) TryUpdateEngine(ctx context.Context) error {
    // 省略部分代码...
    fc := eth.ForkchoiceState{
       HeadBlockHash:      e.unsafeHead.Hash,
       SafeBlockHash:      e.safeHead.Hash,
       FinalizedBlockHash: e.finalizedHead.Hash,
    }
    
    fcRes, err := e.engine.ForkchoiceUpdate(ctx, &fc, nil)
    if err != nil {
       // 省略部分代码...
    }
    if fcRes.PayloadStatus.Status == eth._ExecutionValid _{
       e.emitter.Emit(ForkchoiceUpdateEvent{
          UnsafeL2Head:    e.unsafeHead,
          SafeL2Head:      e.safeHead,
          FinalizedL2Head: e.finalizedHead,
       })
    }
    if e.unsafeHead == e.safeHead && e.safeHead == e.pendingSafeHead {
       // Remove backupUnsafeHead because this backup will be never used after consolidation.
       e.SetBackupUnsafeL2Head(eth.L2BlockRef{}, false)
    }
    e.needFCUCall = false
    return nil
}
```

会再次调用一次 `engine_forkchoiceUpdate` 方法，但这次没有 attributes 参数。执行完这个方法之后，执行层的区块状态才真正的固定。

## 三个 engine API 的作用

### **engine_forkchoiceUpdated**

用于更新共识层的分叉选择状态。

第一个参数分别定义了 head、safe、finalized，三个状态的区块 hash，用来确定最新的区块头。

第二个参数 PayloadAttributes，则包含了下个区块的部分数据，包括交易等。

调用这个接口后，执行层客户端，会根据第一个参数决定自己的区块头。

如果第二个参数 `PayloadAttributes` 不是空，那么还会 `PayloadAttributes` 中取出交易，以及从 mempool 中取出交易执行，交易执行后，新的区块产生的修改的状态会被保存在内存中，供后续的流程使用。

对这次生成的 Payload 信息生成一个唯一标识的 payloadId，后续用户可以使用 payloadId 来查询 Payload 数据。

但 PayloadId 在每个区块相当于是固定的：

```go
func (args *BuildPayloadArgs) Id() engine.PayloadID {
    hasher := sha256.New()
    hasher.Write(args.Parent[:])
    binary.Write(hasher, binary.BigEndian, args.Timestamp)
    hasher.Write(args.Random[:])
    hasher.Write(args.FeeRecipient[:])
    rlp.Encode(hasher, args.Withdrawals)
    if args.BeaconRoot != nil {
       hasher.Write(args.BeaconRoot[:])
    }
    var out engine.PayloadID
    copy(out[:], hasher.Sum(nil)[:8])
    out[0] = byte(args.Version)
    return out
}
```

Parent：父区块 hash。

Timestamp：区块时间。

Random：区块随机值。

FeeRecipient：接受交易消耗的 Gas 费的地址，L2 中固定为一个合约地址。

Withdrawals：提现列表，每个区块是固定的。

BeaconRoot：有 CL 客户端提供同样是固定的。

通过这些字段生成一个 hash，并把 hash 的首个 byte 替换为 **engine_forkchoiceUpdated** 的版本对应的固定值。

### **engine_getPayload**

用户在拿到 payloadId 之后，就可以请求到有效的 Payload 的数据。

共识层客户端可以通过 Payload 数据提前做一些判断，看区块数据部分数据是否符合规范，提前做一些验证。

该 API 用于获取特定有效负载的详细信息。有效负载是指待执行的交易和状态变化。通过这个接口，客户端可以请求特定有效负载的内容，以便进行验证或其他操作。

### **engine_newPayload**

该 API 用于提交新的有效负载到执行层。

但是这一步中 Payload 数据已经包含交易、父区块 hash、当前区块 hash、以及执行交易后链上状态的 stateRoot 等信息。

当执行层客户端收到 Payload 数据之后，会将交易列表、withdrawls 等比较容易校验的 hash 的值都比较一遍。

校验通过后，还需要将 block 中的交易执行一遍之后，再次检查区块中的 stateRoot 与 Payload 中携带的 stateRoot，以及产生的区块的 hash 以及 Payload 中携带的 hash 是否都一致。

通过各种校验之后，最终才会把区块保存下来，并更新链的状态。
